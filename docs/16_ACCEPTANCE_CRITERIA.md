# 16. 수용 기준

각 변경은 기능 결과와 실제 검증 증거가 있을 때 완료합니다. 다음은 공통 확인 기준입니다.

- CLI와 Web에서 동일한 버전·권한·중복 방지 규칙을 적용한다.
- 신뢰할 수 있는 합성 Research → Compose → archive → SMTP double 흐름이 원문·첨부 hash를 유지한다.
- 동시 enqueue·claim·수신자 변경·취소·전송 경쟁에서 두 번 실행·발송하지 않는다.
- 결과 경로·JSON·HTML·첨부·수신자 결합의 무결성 실패를 실제 전송으로 넘기지 않는다.
- DATA 이후 불확실 상태를 자동으로 미발송/성공 처리하거나 재전송하지 않는다.
- 원래 논리 날짜, Task 버전, 부모 입력과 과거 archive를 재시도에서 보존한다.
- 관리자·사용자·조회자의 목록·개별 파일·변경 권한과 소유자 범위를 모두 검사한다.
- 설치·backup/restore·migration은 기존 자료를 보존하고 혼합 버전 실행을 피한다.
- 운영 정보가 공개 예제·문서·배포 artifact에 들어가지 않는다.

테스트하지 않은 native provider·실제 SMTP·TLS·kernel·브라우저 조건은 검증 공백으로 남깁니다. 코드 구현과 특정 호스트의 운영 readiness, 기능 성공과 강제 격리를 분리해 평가합니다. [테스트 전략](15_TESTING_STRATEGY.md)과 [릴리스 범위](STATUS.md)를 따릅니다.
